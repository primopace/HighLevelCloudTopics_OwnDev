Why Outbox Pattern Exists

Problem scenario:

Save Exam Result → DB success
Publish Event → RabbitMQ fails

Result:

Other microservices never receive event

System becomes inconsistent.

5️⃣ Outbox Pattern Solution

Instead of publishing immediately:

1. Save business data
2. Save event in Outbox table
3. Commit transaction

Later:

Background service
    ↓
Reads Outbox table
    ↓
Publishes events to RabbitMQ

Flow:

Exam Evaluated
      ↓
Save ExamResult
      ↓
Save OutboxEvent
      ↓
Transaction Commit
      ↓
Background Worker
      ↓
Publish Integration Event
      ↓
RabbitMQ
      ↓
Other Microservices

7️⃣ Why This Pattern Is Important

Without domain events:

Controller
   ↓
Service
   ↓
Repository
   ↓
Notification
   ↓
Cache
   ↓
RabbitMQ

Everything becomes tightly coupled.

With domain events:

Domain Event
   ↓
Independent Handlers

Each feature becomes loosely coupled.

8️⃣ Production Rule

Domain event handlers should:

✔ Execute business side effects
✔ Be small and focused
✔ Be independent

They should NOT:

❌ Contain core business logic
❌ Modify the same aggregate again
❌ Create circular dependencies

Eventual consistency in .NET microservices is a distributed data model where services update their own data stores independently, 
allowing temporary inconsistencies across the system. Instead of immediate locking, services synchronize asynchronously via events
(e.g., RabbitMQ, Kafka) or sagas, ensuring all nodes converge to a consistent state over time.
